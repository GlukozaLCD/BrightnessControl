# BrightnessControl — проектный план

Desktop-приложение для Windows 11: управление яркостью подключённых
мониторов (по отдельности и всех сразу), с трей-доступом и
автоматизацией по сценариям.

Порядок работы над проектом подчиняется иерархии планирования:
проектный план (этот файл) → функциональный план (`.plans/PLAN_<slug>.md`,
только локально, в `.gitignore`) → фазы → этапы → пункты/вопросы.
Каждая фаза функционального плана начинается с вопросов пользователю и
не выполняется без подтверждения.

## Идейные столпы

1. **Универсальное управление яркостью** — единый API "яркость по
   монитору" и "яркость всех сразу". Источники: DDC/CI (внешние
   мониторы), WMI/`WmiMonitorBrightnessMethods` (встроенная панель
   ноутбука), программный fallback (например, gamma-коррекция или
   оверлей-затемнение) для мониторов без поддержки DDC/CI — это не
   гипотетический, а реальный кейс в имеющемся оборудовании.
2. **Мгновенный доступ через трей** — иконка в трее, скролл колеса мыши
   над ней меняет глобальную яркость. Поведение скролла (вкл/выкл,
   "проценты 0–100" против "циклическое переключение между
   пресетами") — настраивается, а не жёстко зашито.
3. **Полноценный GUI (Avalonia)** — детальная настройка каждого
   монитора, групповое управление, отдельная категория настроек
   "Поведение трея". Любое окно, открытое из трея (клик/меню),
   обязано появляться на том мониторе, где физически произошло
   взаимодействие, а не только на основном мониторе системы.
4. **Контекстная автоматизация** — три вида правил:
   - расписание по времени суток;
   - профили яркости, привязанные к активному приложению/окну;
   - адаптивное затемнение по бездействию: настраиваемый idle-таймаут
     (в минутах) → приглушение яркости → автоматическое восстановление
     исходных значений при возврате активности пользователя.
5. **Устойчивость к разнородному оборудованию** — программный fallback
   обязателен для мониторов без DDC/CI, а не опционален.
6. **Гибкое хранение настроек** — при первом запуске пользователь
   выбирает режим: portable (конфигурация рядом с exe) или обычный
   (в профиле пользователя, `%AppData%`). Выбор сохраняется.

## Технологический фундамент

- **Целевая платформа сейчас: только Windows 11.** Кроссплатформенность
  не является текущим требованием, но при прочих равных
  предпочитаются решения, не закрывающие путь к будущему переносу.
- **GUI-стек: Avalonia** (XAML/MVVM, как WPF, но кроссплатформенный по
  своей природе; включает системный трей API). WPF был отклонён
  осознанно — он исключительно для Windows и потребовал бы полного
  переписывания GUI-слоя при будущем портировании.
- **Язык/платформа:** C#/.NET (актуальная LTS-версия), финальный
  артефакт — `.exe` под Windows 11.
- **Яркость:** DDC/CI (внешние мониторы) + WMI (встроенная панель) +
  программный fallback (мониторы без DDC/CI).
- **Версионирование:** семантическое версионирование приложения
  (semver), начиная с ранней версии — точная стартовая версия
  уточняется в FP7. Кроссплатформенность — отдельное измерение,
  которое пока не в фокусе.
- **Git:** репозиторий
  [GlukozaLCD/BrightnessControl](https://github.com/GlukozaLCD/BrightnessControl)
  на GitHub. Локальная identity этого репозитория:
  `GlukozaLCD <321587875+GlukozaLCD@users.noreply.github.com>` —
  единственная сохранённая GitHub-учётка на машине, конфликтов нет.
  Функциональные планы (`.plans/PLAN_*.md`) в репозиторий не попадают.

## Реестр функциональных планов

| # | Статус | Функциональный план | Суть |
|---|---|---|---|
| FP1 | готово (2026-09-05) | Ядро управления яркостью | `BrightnessControl.Core`: обнаружение и классификация мониторов, DDC/CI + WMI + оверлей-fallback, единый `BrightnessController` ("по монитору"/"все сразу"), персистентность, реакция на переподключение. Проверено на реальном оборудовании (3 монитора). Известная особенность: некоторые DDC/CI-мониторы ("смарт"-панели) иногда не подтверждают запись с первого раза — провайдер это обнаруживает и честно сообщает о неудаче, вызывающий код должен быть к этому готов |
| FP2 | готово (2026-09-05) | Системный трей | `BrightnessControl.App` (Avalonia): собственная иконка через `Shell_NotifyIcon` (не Avalonia `TrayIcon` — та не даёт событий скролла), скролл над иконкой (точный hit-test через `Shell_NotifyIconGetRect` + `WH_MOUSE_LL`) меняет глобальную яркость (шаг настраиваемый), HUD с процентом у курсора. Правый клик по иконке напрямую открывает окно настроек (FP3) — контекстное меню убрано полностью по ходу FP3, "Выход" переехал во вкладку окна настроек |
| FP3 | готово (2026-09-06) | GUI детальной настройки | Окно настроек (вкладки "Мониторы"/"Трей"/"Оформление"): слайдеры по каждому монитору + синхронизирующий "Все сразу" (прилипание к настраиваемому шагу, кнопки ±1%), гибридные "липкие" значения для скролла трея (не жёсткий режим, а магнитные точки на плавной шкале), выбор темы. Открывается как оверлей на мониторе клика — без рамки, `Topmost`, закрывается по клику мимо; кастомный крестик закрытия с анимацией. Контекстное меню трея убрано полностью — правый клик открывает окно напрямую. Проверено на реальном оборудовании. Открытые вопросы явно вынесены в FP7 (portable-режим), FP9 (позиционирование окна и общая навигация) |
| FP4 | готово (2026-09-06) | Автоматизация: расписание по времени | Ежедневное ступенчатое расписание (правило действует от своего времени до следующего): `ScheduleRule`/`ScheduleSettings`/`ScheduleEngine` (Core, фоновый таймер, работает независимо от открытости окна), область действия на правило (все мониторы/конкретные), ручная корректировка временно перебивает расписание до следующей точки. Вкладка "Расписание" с живым индикатором активного правила по монитору. Подтверждено живым тестом на реальном оборудовании (переход с ручного override на новое правило точно в срок). Форма создания правила пользователю показалась неудобной — переделка дизайна отложена в FP9 |
| FP5 | готово (2026-09-06) | Автоматизация: профили по приложению | Отслеживание переднего окна через `SetWinEventHook` (`ForegroundAppWatcher`, Core), `AppProfile`/`AppProfileSettings`/`AppProfileEngine`: профиль применяется ТОЛЬКО к монитору, на котором сейчас физически находится окно совпавшего приложения (определяется динамически через `MonitorFromWindow` при каждой смене переднего окна) — без статичного списка мониторов и без дебounce. При выходе из профиля восстанавливается снимок значения "до профиля". Вкладка "Профили приложений": процесс из списка запущенных (AutoCompleteBox с подсказками по мере набора + кнопка показа всех + скрытие/восстановление ненужных процессов) или заголовок окна текстом, живой индикатор "сейчас активно". Приоритет между FP4 и FP5 решён: профиль приложения приоритетнее расписания — пока он активен, `ScheduleEngine` этот монитор игнорирует (`isMonitorSuppressed`), а при выходе из профиля восстанавливается АКТУАЛЬНОЕ на данный момент значение расписания, а не устаревший снимок. Проверено юнит-тестами и живьём на реальном оборудовании (переключение приложений между мониторами, взаимодействие с активным расписанием) |
| FP6 | готово (2026-09-06) | Автоматизация: адаптивное затемнение по бездействию | Простой определяется опросом `GetLastInputInfo` (Win32) — нет системного события, поэтому периодический `Timer` (`IdleEngine`, Core), интервал опроса настраиваемый (`IdleSettings.PollIntervalSeconds`, по умолчанию 1с). Приглушение — глобальное на ВСЕ мониторы разом, один настраиваемый процент (не per-monitor, в отличие от расписания). Восстановление по тому же приоритету, что и FP4×FP5: активный профиль приложения → текущее правило расписания → "сырой" снимок до простоя. `ScheduleEngine` игнорирует все мониторы, пока приглушение активно. Вкладка "Простой": включить/выключить, таймаут (мин), процент яркости, интервал опроса, живой индикатор "сейчас приглушено". По ходу живой обкатки найдены и исправлены два реальных бага: последовательная (а не параллельная) запись при восстановлении вызывала заметное отставание от приглушения (добавлен `BrightnessController.SetEachBrightness`), и гонка в `IdleEngine` — таймер не ждал завершения предыдущего тика, из-за чего при коротком интервале опроса приглушение иногда "залипало" без восстановления (исправлено блокировкой). Подтверждено живым тестом на реальном оборудовании |
| FP7 | не начат | Упаковка и дистрибуция | Выбор portable/обычный режим на первом запуске (включая недоступность portable при неписьменной папке установки — см. заметку в FP3), автозапуск, семантическое версионирование |
| FP8 | не начат | Кастомная иконка приложения/трея | Идея пользователя: иконка-"солнышко", визуально показывающее уровень общей яркости через степень "заполненности" (например, 80/50/20%) — акцент на стиль, а не строго функциональность, но открыто для функциональных идей, если появятся |
| FP9 | готово (2026-09-06) | Навигация и расположение UI | Крупный редизайн вместо изначальных трёх мелких пунктов. Тонна пояснительного текста убрана в `ToolTip`. Иконка трея: левый клик открывает лёгкий `GlobalSliderPopup` (только общий слайдер, прицеплен к иконке), стрелка разворачивает ОТДЕЛЬНОЕ окно `MonitorSlidersPopup` с индивидуальными слайдерами — два независимых окна, ведущих себя как одно целое для клика мимо, но не мешающих друг другу; правый клик открывает `SettingsWindow` (тоже прицеплено к иконке трея вместо центра монитора), из которого слайдеры полностью убраны. `SettingsWindow`: `TabControl` заменён двухуровневым боковым списком категорий ("Настройки"/"Автоматизация" с подкатегориями), с кнопкой-иконкой (диаграмма макета, не стрелка) для переброски списка между правым и левым краем окна. Форма создания правила расписания переделана: заголовки колонок, карточка для новой записи, время — кастомный контрол с прокруткой колеса (± к целому числу, Shift — по цифре точнее) вместо `TimePicker`/`NumericUpDown`. Акцентный цвет Windows — `AccentColorService` через `FluentTheme.Palettes[variant].Accent` (не плоские ресурсы — те не сработали на практике), с переключателем в "Оформление"; внешний вид дополнительно переделан по образцу Volumey (сплошной тёмный фон, без рамки сайдбара, акцентная полоска под заголовком). По ходу живой обкатки найдено и исправлено несколько реальных багов: слайдер-пузырёк с процентом, обкатанный несколько раз (фиксированная ширина, позиционирование через `LayoutUpdated`); настоящая причина "наезжающего" текста в поповере — не в бегущей строке, а в пропущенном параметре ширины у одного вызова; дрожь подписей при каждом изменении процента (нефиксированная ширина Auto-колонки); упрощение названий безымянных мониторов до идентификатора адаптера. Подробности всех фаз — в истории git |
| FP10 | не начат | Визуальный конструктор автоматизации | Идея пользователя (2026-09-06): drag-and-drop холст, где пользователь собирает СВОИ правила профилей приложений — объединяет триггеры по времени (FP4) и по процессу (FP5) в один гибкий блок вместо двух раздельных механизмов. Приглушение по бездействию (FP6) в конструктор не входит — остаётся отдельным жёстко заданным приоритетом. Приоритет по умолчанию — стандартный (простой → профиль/время → расписание, как сейчас), но правило может нести необязательный блок "приоритет" с числом, переопределяющим порядок именно для него. Сложность не в самом холсте (Avalonia не имеет готового node-editor контрола, но это решаемо), а в проектировании безопасной общей модели исполнения — сейчас приоритет зашит в коде, а не в данных. Требует отдельного функционального плана и обдумывания модели ДО реализации UI |

Порядок: FP1 (ядро) → FP2/FP3 (интерфейсы доступа, опираются на ядро) →
FP4–FP6 (автоматизация, опирается на ядро и GUI) → FP7 (упаковка).

По завершении всех этапов функционального плана — он сворачивается в
краткую запись в этой таблице (статус "готово" + дата), а временный
`.plans/PLAN_<slug>.md` удаляется.
